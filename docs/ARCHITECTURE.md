# 架构与维护

## 目录

```text
app/
  launcher.py           短时启动、无窗口后台进程、日志和已有服务检测
  server.py             本地 HTTP 接口、SQLite、扫描、导入、删除恢复及导出
  receipt_jobs.py       入库单任务、隔离副本、草稿与失败恢复
  receipt_layout.py     模板空段整理及缺失字段留空
  statistics_table.py   配套统计表、固定类别、金额和文档写入
  invoice_company.py    销售方识别、水印污染检查和 PDFium 锁
  pdf_layout.py         按坐标重建横向文字，排除旋转水印
  invoice_extract.py    自动提取校验、布局回退、单商品折扣及批量部分结果
  folder_picker.py      Windows 文件夹选择窗口
  web/                  原生前端，静态文件直接提供，无构建步骤
  assets/               空白入库单、统计表模板和启动图标
  vendor/ruku/          MIT 上游脚本、许可、来源和 SHA256
  test_*.py             隔离的后端回归
  test_*.cjs            前端行为回归
  data/                 运行生成，不入库
invoices/               默认票据目录，实际内容不入库
```

## 运行边界

服务绑定回环地址，变更接口检查 Host、Origin 和每次进程随机生成的工作台密钥。应用不是多用户财务服务器，不要将监听地址改成公网地址后直接部署。没有登录系统，也没有联网识别或遥测。

SQLite 保存字段和操作历史。文件原文保留在原位置，手动导入副本在 data/imports。回收站使用软删除记录和文件移动，恢复时检查目标冲突；批量操作先验证全部输入，再执行带回滚的变更。ZIP 只打包明确选择的原件，校验哈希和体积，同名文件添加编号。

分类列表由后端按固定顺序提供，新增住宿费，前端筛选保留这一顺序，并显示尚无票据的有效分类。类型修改及历史继续使用既有校验和事务。

`is_itinerary` 在 state 返回前排除行程单附件，之后才执行去重；页面统计、筛选、全选及台账导出都使用同一可见发票集合。识别依据文件名、标题和文档开头，明确发票抬头优先，不删除记录或文件。回归见 `test_itinerary_visibility.py`，覆盖旧记录、重复扫描、ZIP 再导入、去重和导出。

CMD 和 VBS 入口经 scripts/start.ps1 调用 app/launcher.py。启动器将服务放在独立后台进程中，标准输入关闭、输出直接写入 app/data 的两个 server 日志，启动器退出后服务继续运行。Windows 子进程使用 CREATE_NO_WINDOW 和 CREATE_NEW_PROCESS_GROUP。启动失败时保留日志并返回非零退出码。

启动器优先通过轻量 /api/health 检查应用标记和数据目录；该接口不读取台账或等待生成锁，仍检查 Host。旧服务缺少此接口时才回退到 /api/state。启动服务先取得独占端口，再初始化数据库，避免重复启动重置运行任务；直接运行 server.py 的前台方式仍可用。启动失败会释放连接；旧入库单被占用时显示维护提示，其他功能继续可用。

## 入库单

默认使用仓库内置的三个 ruku 脚本，顺序为提取、重命名、填表，均在 `app/data/receipts/<任务>/` 的独立副本中执行。识别失败时用户可以补填或将缺失值留空后继续。续跑保留识别原文和草稿，用兼容 JSON 调用原脚本，完成后清空文档中的未知占位值。任务状态、补填草稿和操作记录保持一致；线程启动失败可重试。

替换模板必须保留 OOXML 结构：首个表格含项目标题及两个空白项目行；第二表格用于商品、合计和签字。`receipt_layout.py` 与上游 fill_receipt.py 的单元格索引依赖这些结构。不能将任意 Word 表格直接替换为模板。

列表及下载接口只使用成功生成且成品仍存在的任务记录，不递归扫描当前或历史发票目录中的 DOCX；模板、测试文档和手工文件不列入。生成结果仅保留最近五组；只清理生成器自己的任务目录，其他用户文档保留。定期完整备份 data 和发票目录；只有数据库备份不足以恢复所有文件。

统计表派生自同一任务的正式 `invoice_data.json`，作为每组入库单的附件，不增加留存组数。类别仅允许试剂、仪器、耗材；名称和价格由任务生成，网址和安全等级默认空白。公司优先使用同哈希原票的销售方，必要时从任务副本提取，明确混入水印的旧公司名可修复，正常手工公司保留。统计表保存先写临时 DOCX 再替换，并与数据库及审计记录保持一致；数据库保存失败则恢复原文件。统计表失败不丢弃入库单，可单独重试。

销售方升级使用独立 `company_parser_version=2`，通用 `parser_version=3` 保持不变，避免重新解析旧台账的其他字段。PDFium 文字和预览共用锁。提取适配层不修改 vendor 中三个原脚本：先核对数值，失败时按横向字符坐标重建，明确的单商品折扣只在品名、类目、税率一致时自动归属；有疑点的记录仍进入补填。批次处理全部来源并保存成功结果后再汇总错误，旧失败任务也可在无人工草稿时只读重建。原始提取结果保存在任务的 `invoice_data_extracted.json`，回退来源记录在任务及步骤日志中。

统计表弹窗使用固定标题区域与独立滚动正文，关闭按钮不随正文滚动。编辑、补填和下载接口继续使用原有来源与工作台密钥校验。

## 发布前检查

运行所有 Python 和前端回归，审查将提交的文件清单。不要发布 data、invoices 实际内容、带真实票据的截图、浏览器下载、验收记录、原始识别 JSON、个人绝对路径或凭据。更新模板时检查 DOCX 内部属性、外部链接、批注和缩略图是否含个人信息。
